# ADR 0009: Data Ownership and Transaction Boundaries

- Status: Accepted
- Date: 2026-07-27

## Context

The control plane needs a consistent relational boundary for authentication records, projects,
audits, and durable job projections. Request handlers, Temporal workflows, and specialized workers
must not share implicit sessions or attempt distributed transactions across PostgreSQL, Temporal,
MinIO, Redis, and Qdrant.

## Decision

PostgreSQL is authoritative for application identities, refresh-token lifecycle state, projects,
audit logs, and job-event projections. Temporal remains authoritative for workflow execution and
history; MinIO owns large immutable bodies; Redis owns ephemeral coordination data; and Qdrant owns
rebuildable retrieval indexes. Relational rows store identifiers, state, lineage, and object keys,
not large workflow payloads.

Each FastAPI operation that mutates relational state receives one request-scoped `AsyncSession`
inside an explicit `session.begin()` boundary. Successful dependency completion commits; any
exception rolls the complete transaction back. Repositories and domain services may flush when an
ID or constraint result is needed, but they never commit or create sessions. Scripts and workers
use the same explicit `DatabaseManager.transaction()` context and own their boundary locally. There
are no module-global sessions.

User and project records use SQLAlchemy optimistic version columns. Conflicting writes fail rather
than silently replacing another user's edit. Lifecycle statuses are constrained strings, not
database-native enums, so their vocabulary can evolve through ordinary reviewed migrations. UUIDs
are generated by the application, timestamps are timezone-aware and normalized to UTC, and JSONB
accepts only explicitly supported JSON primitives and normalized UUID/date values.

Audit records are staged in the same transaction as the decision they describe. Cross-store work
is coordinated only after committed relational state exists, using IDs and object keys. It relies
on idempotent Temporal activities and reconciliation instead of pretending that a PostgreSQL
transaction can atomically commit an object, vector, cache entry, or workflow execution.

Alembic is the only schema-change mechanism. Migrations run as a separate operational step and
never during API startup or request handling.

## Consequences

- Transaction ownership is visible at FastAPI dependency, script, and worker entry points.
- Repository unit tests can use fake sessions without PostgreSQL, while migration and concurrency
  behavior is verified against an explicitly configured disposable PostgreSQL database.
- Long-lived or nested business transactions are avoided; external calls must not occur while a
  request transaction remains open.
- Future multi-tenant tables must add tenant ownership and authorization filters without changing
  these session and commit rules.
- Reliable cross-store publication may require an outbox or equivalent durable workflow command in
  a later schema revision.
